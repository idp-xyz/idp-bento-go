# 维护与发布治理

状态：已确认

## 治理原则

- TMS 与 Parcel 都是消费者，任何一方都不是框架宿主。
- 共享框架仓库必须由公司控制的 GitHub Organization 拥有；个人账号可以担任维护者，但不能作为仓库最终 owner 或发布信任根。
- 目标维护组不少于 3 人，并覆盖两个消费者的技术视角；任何单一消费者不能独自满足公共契约变更的审批条件。人数达成前按「当前治理模式」运行，机器门禁替代职责分离。
- 维护者负责框架质量、兼容性、发布和安全，不拥有消费者业务规则或发布计划。
- 消费者代表负责证明真实使用场景和兼容性，不因此获得修改另一个消费者代码、数据或 CI 的权限。
- 合并权限和发布权限分离：维护者批准合并，受保护 CI 在满足门禁后创建 Ruleset 保护的 tag，并以 DSSE 签名授权绑定版本、提交和候选证据。
- 禁止个人直接创建稳定 tag、覆盖版本、强推默认分支或绕过必需检查。

## 角色与职责

| 角色 | 职责 | 默认权限 |
| --- | --- | --- |
| 框架维护者 | 设计审查、代码评审、兼容性判断、漏洞处置和发布批准 | 审批与受保护分支合并；无个人稳定发布权限 |
| TMS 消费者代表 | 评审共享契约对 TMS 的影响，维护 TMS `bento-contract` | 消费者评审和合同证明；无框架发布凭据 |
| Parcel 消费者代表 | 评审共享契约对 Parcel 的影响，维护 Parcel `bento-contract` | 消费者评审和合同证明；无框架发布凭据 |
| 安全批准者 | 评估漏洞等级、披露范围和紧急处置 | 安全变更批准；不能单独合并或发布 |
| CI 发布身份 | 校验门禁、签署 DSSE 发布授权、创建受保护 tag、生成 provenance 和发布 module | 仅自动化发布；短期凭据、最小权限 |

同一人员可以承担多个评审角色，但一次高风险变更所需批准必须来自相互独立的账号；作者不能用自己的批准满足全部门禁。

## 变更分级与门禁

「最低门禁」列在目标形态下是人工评审，在当前的单维护者模式下由机器门禁承担。两列同时列出，第二名维护者到位时按目标形态恢复第一列，无需重写表结构。

| 变更类型 | 最低门禁（目标形态） | 最低门禁（`SOLO_BOOTSTRAP`） | 必需验证 |
| --- | --- | --- | --- |
| 文档、注释、内部重构且不影响公共行为 | 1 名非作者维护者 | 框架 PR CI 通过 | 框架 PR CI |
| 实验性适配器内部实现，公共签名和迁移不变 | 1 名非作者维护者 + 受影响消费者代表 | 框架 PR CI 通过；候选阶段该消费者合同通过 | 框架 PR CI；发布候选阶段双消费者合同 |
| 公共 API、错误语义、事件信封、事务语义或兼容性策略变更 | 2 名非作者维护者 + TMS 代表 + Parcel 代表 | `candidatecheck` 全门禁通过 + 双消费者对同一候选 `PASS` + 24 小时冷静期 | apidiff/行为变化报告、框架 PR CI、迁移说明、同一候选的双消费者合同 |
| PostgreSQL 技术迁移、持久化格式或破坏性适配器变更 | 2 名非作者维护者 + TMS 代表 + Parcel 代表 | 同上，且空库与升级测试均在真实 PostgreSQL 16 上通过 | 空库/升级测试、回退说明、同一候选的双消费者合同 |
| 安全修复 | 2 名非作者维护者 + 安全批准者；影响公共契约时仍需双消费者代表 | 同上，且披露时点由维护者单方决定并记入证据 | 安全测试、框架 CI、适用消费者合同和受控披露 |

公共 API 新增也按公共契约变更处理，避免用“兼容新增”绕过消费者所有权审查。

## 当前治理模式

本仓库当前只有一名维护者，`GovernanceMode` 为 `SOLO_BOOTSTRAP`。目标形态要求的职责分离由机器门禁承担，缺失的保证是**独立人工判断**，且该缺失随每次发布证据一同公布。

机器门禁覆盖的部分——它们与维护者人数无关，一人也无法绕过：

- `candidatecheck` 的仓内候选门禁，含精确工具链、module 身份、apidiff、行为清单、依赖图与无缓存全量测试。
- `proofcheck` 对同一候选、同一合同套件版本的双消费者比对。
- `evidencecheck` 对 manifest、原始证明摘要、来源字段与协调时间窗的校验。
- tag Ruleset 防移动、WORM `COMPLIANCE` 三年保留、DSSE 绑定版本与目标提交。

它们防的是手滑、事后篡改、版本号复用和跳过测试。它们防不了单人判断错误——没有第二个人复核这次改动**是否应该做**。

因此稳定发布的信任边界是：构建来源与测试结果可证明且不可篡改，设计判断只经过一个人。读者据此自行决定采信程度，而不是从「双维护者已批准」这类无法兑现的声称里推断。

第二名维护者到位时，把变更分级表的目标形态列恢复为生效列，`GovernanceMode` 改为对应取值，披露字段随之变化；本节保留作为历史记录。

## 分支与发布保护

- 默认分支禁止直接推送、强推和删除，必须通过 PR 和必需检查。
- `CODEOWNERS` 或等价规则必须覆盖公共核心、实验性适配器、迁移资产、CI 和发布配置。
- 稳定版本只由 CI 发布身份创建；tag 必须受 Ruleset 保护且不可移动，DSSE 发布授权必须签名绑定版本、提交、候选 module 校验和和双消费者合同证明。
- 发布制品不可覆盖；发现发布错误时创建新补丁版本或撤销可见性，不复用原版本号。
- 发布凭据使用短期身份或受保护密钥，维护者个人设备不保存长期发布令牌。
- 权限变更、维护者增删、发布失败和例外处置必须留下可审计记录。

## 紧急例外

- 已知消费者合同失败时，不得通过例外创建稳定版本。
- CI 平台故障时，可以由消费者在自己的安全边界内运行等价合同并提供可验证证明；这是替换执行通道，不是跳过测试。
- 严重安全问题可以加速候选、评审和披露，但仍需框架必需测试及两个消费者的有效合同证明。
- 无法取得完整门禁时只能发布或保留预发布候选，不得伪装为稳定兼容版本。
- 每次紧急处置必须记录原因、批准者、受影响版本、临时措施、补验结果和关闭时间。

## 人员与权限绑定门禁

在开放共享合并或创建首个发布候选前，必须完成：

1. 将框架仓库绑定到公司控制的 GitHub Organization，并核验新的 owner ID；迁移后重新验证 repository ID、默认分支、Git transport 和 vanity 目标。
2. 指定不少于 3 名框架维护者。在此之前按「当前治理模式」运行，并在每次发布证据中公布单维护者事实。
3. 分别指定 TMS、Parcel 消费者代表和安全批准者。
4. 创建受保护默认分支、评审规则和 CI 发布身份。
5. 验证任何单一个人或单一消费者都不能绕过公共契约门禁发布稳定版本。单维护者模式下这一条对机器门禁成立、对人工判断不成立，差额由披露而非由声称覆盖。
6. 记录维护者离任、账号失陷和凭据轮换流程。
