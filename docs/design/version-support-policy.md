# 版本兼容性与支持策略

状态：已确认

## 目标

为 TMS 与 Parcel 提供可预测但有限的独立升级窗口，明确哪些版本获得兼容性、缺陷和安全修复，同时避免 `idp-bento-go` 在早期形成无限维护分支。

## 已确认策略

| 版本线 | 全量支持 | 降级支持 | 结束条件 |
| --- | --- | --- | --- |
| `v0.x` | 最新 minor | 前一 minor 在后继 minor 发布后继续获得 90 天关键修复 | 90 天期满后进入 `EOL` |
| `v1.x` | 最新 minor | 每个被后继 minor 取代的版本继续获得 6 个月关键修复 | 对应 6 个月窗口期满后进入 `EOL` |
| `v1` 在 `v2.0.0` 发布后 | `v2` 成为当前主版本 | 最新 `v1` minor 获得 12 个月关键修复 | `v2.0.0` 发布 12 个月后进入 `EOL` |

首个版本发布前尚无实际日历日期。每次 minor 或 major 发布时，release notes 必须给出所有受影响版本线的明确支持状态和 EOL 日期。

## 支持状态

### `FULL`

- 接收兼容缺陷修复、安全修复、文档修正和必要性能修复。
- 运行框架完整测试、迁移升级测试以及 TMS、Parcel 最小消费者合同。
- 新功能只进入当前 `FULL` minor，不回补到旧 minor。

### `SECURITY`

- 只回补高危安全问题、认证或授权绕过、跨租户/跨范围数据泄露、数据损坏或丢失、不可恢复迁移缺陷，以及阻断支持版本升级的严重兼容性回归。
- 不回补新功能、普通缺陷、非关键性能改进或 API 便利性调整。
- 每个回补版本仍必须通过该维护线的框架测试、迁移测试和两个消费者合同。

### `EOL`

- 已发布 tag 和校验和保持不可变，但不再承诺新补丁、消费者合同、Go 工具链适配或依赖漏洞修复。
- 消费者必须升级到 `FULL` 或 `SECURITY` 状态的版本线后才能获得修复。

## SemVer 规则

- `v0.x` 的破坏性公共 API 变化只能进入新的 minor，必须提供迁移说明、双消费者合同结果和明确的前一 minor EOL 日期。
- `v0.x` patch 不得包含已知破坏性公共 API、事件信封或数据库迁移变化。
- `v1` minor 必须向后兼容；任何公共 API、事件线格式或持久化契约的破坏性变化只能进入 `v2`。
- `v1` 中废弃的公共能力至少保留一个稳定 minor 且不少于 6 个月，并且只能在下一 major 删除。
- 已发布迁移资产和事件版本不可重写；兼容修正通过新迁移、新事件版本或新补丁实现。
- 每次候选使用逐包 apidiff snapshot、编译夹具、版本化行为清单和双消费者合同比较上一发布版本；更新当前 snapshot 不能替代历史比较。
- 同一 Envelope SpecVersion 的旧合法输入不得因框架升级变为非法；更严格规则进入新版本，并在支持窗口内继续接受历史版本。

## 支持矩阵

仓库必须维护版本支持矩阵，至少包含：

| 字段 | 含义 |
| --- | --- |
| Framework line | 例如 `v0.3.x` 或 `v1.4.x` |
| Status | `FULL`、`SECURITY` 或 `EOL` |
| Start date | 版本线开始日期 |
| EOL date | 明确结束日期；当前线可以为 `UNBOUND` |
| Go toolchain | 验证的精确 Go 补丁版本 |
| PostgreSQL range | 验证的数据库主版本范围 |
| TMS contract baseline | 合同验证使用的消费者提交或分支 |
| Parcel contract baseline | 合同验证使用的消费者提交或分支 |

日期、工具链和消费者提交必须由 CI 生成或校验，不能只依赖手工说明。

## 回补与发布规则

- 维护分支只从对应已发布 minor 建立，不从消费者仓库复制框架源码。
- 修复先进入当前开发线；需要支持旧线时，以最小补丁显式回补并重新执行该线门禁。
- 已知合同失败不得以“安全修复”为理由绕过。若消费者 CI 不可用，使用治理文档允许的等价合同证明。
- 不能安全回补时，安全公告必须说明受影响版本、缓解措施和推荐升级目标；不得把未经验证的修复标记为兼容补丁。
- 本策略定义支持期限，不承诺漏洞响应小时数或商业 SLA；如需 SLA，必须另行绑定负责人和服务承诺。

## 关键场景

### 发布新的 `v0` minor

发布 `v0.4.0` 时，`v0.4.x` 进入 `FULL`，`v0.3.x` 进入 90 天 `SECURITY`，更早版本进入 `EOL`，除非其既有窗口尚未结束。

### 发布新的 `v1` minor

发布 `v1.5.0` 时，`v1.5.x` 进入 `FULL`，被替代的 minor 从该发布日期起获得 6 个月 `SECURITY`。若较早 minor 的已承诺窗口尚未结束，继续维护到其明确 EOL 日期。

### 发布 `v2.0.0`

`v2` 成为当前全量支持主版本；最新 `v1` minor 从 `v2.0.0` 发布日起继续获得 12 个月关键修复。其他尚未到期的承诺窗口仍按已公布日期执行。

## 未决绑定

- 首个版本发布日期和首份支持矩阵条目。
- 安全响应 SLA；当前只确认支持范围和期限。

`v0.1` 的初始 PostgreSQL 支持范围固定为 major 16，CI 使用当时最新稳定 16.x 补丁；当前设计证据版本为 16.12。新增其他 major 必须先通过完整迁移、catalog、并发和消费者合同矩阵，再进入支持表。
