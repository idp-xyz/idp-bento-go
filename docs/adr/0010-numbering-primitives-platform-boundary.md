# ADR-0010：接收编号原语、拒绝平台能力进入框架

状态：已接受（"原语进入框架 `v0.2`"的路线于同日被 [ADR-0011](./0011-numbering-primitives-move-to-platform-go.md) 取代；能力不进框架的边界部分继续有效）

日期：2026-08-24

## 背景

Python 生态用三层分工解决编号与参照数据的复用：`idp-bento` 拥有编号原语（`FormatTemplate`、Feistel 加扰、校验位），`idp-platform` 在其上组装能力（单据类型目录、预留/认领、选项目录），prism/loms 只做接线。TMS 与 Parcel 的设计文档都出现了运单号/追踪号需求，但两个 Go 消费者目前都没有编号实现代码。若不预先划清边界，能力层会借"复用"名义进入框架公共 API，而框架非目标明确排除没有真实消费者证明的抽象、通用 CRUD 和产品语义。

## 决定

框架接收的编号相关公共 API 以**编号原语**为限：

- 业务无关的编号模板 DSL、Feistel FPE 加扰与校验位，进入纯标准库新核心包 `numbering`（`v0.2` 提案，引入即实验性）。
- 并发安全的原子序列分配作为 PostgreSQL 技术表适配器 `postgres/sequence`（实验性），沿用"框架拥有不可变迁移资产、消费者拥有执行"的既有边界。
- 加扰密钥由消费者持有并通过参数传入，框架不管理凭据。
- 模板令牌词汇表与 Python `FormatTemplate` 保持语义兼容；不承诺 API 形状对等，不承诺加扰或校验位跨语言输出逐位相等。

**平台能力**不进入框架，永久排除：选项目录全部（聚合、作用域继承、变更审计、管理 API）、单据类型目录、编号预留/认领与草稿持有 TTL、DTO 与 HTTP 路由工厂。此类能力的去处（独立 `idp-platform-go` 库或消费者仓库）保持 `UNBOUND`，等真实重复出现后另行决策。

实现时机排在 `v0.1.0` 稳定发布之后；决策简报确认前不开始实现，确认前提是 TMS 与 Parcel 各书面确认一个具体编号用例。

## 后果

- 框架获得两个消费者都需要、并发敏感且容易做错的最小机制；公共面不吸入目录、预留等编排逻辑。
- 能力层被显式挡在框架外，未来提案必须先推翻本 ADR，而不是悄悄扩包。
- 序列适配器复用技术表迁移边界，不新增所有权模式。
- 代价：能力层收敛之前，消费者需要自行组装单据类型目录、预留等编排；跨语言不保证加扰输出一致，未来任何数据迁移需自行换算。

## 考虑过的替代方案

- 整体移植 `idp-platform`（含 options）进框架：违背非目标（通用 CRUD、HTTP 路由、无双消费者证据的抽象），公共面不可控。
- 立即新建 `idp-platform-go` 能力库：两个消费者尚无编号代码，真实重复未出现，立仓时机未到。
- 全部留给消费者各自实现：模板 DSL 与加扰必然分叉出不兼容方言，并发序列分配重复踩坑。
- 与 Python 全面对等（含加扰逐位一致）：锁死 Feistel 轮数与密钥派生等实现细节，违背"不逐项复制 Python bento API"的非目标。
