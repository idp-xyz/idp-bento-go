# ADR-0011：编号原语撤出框架路线，随 idp-platform-go 立库落地

状态：已接受

日期：2026-08-24

## 背景

ADR-0010 接受"框架 `v0.2` 接收编号原语"时的前提是生态中没有平台能力层，能力去处 `UNBOUND`。同日维护者决定立即建立 `idp-platform-go` 能力库（参考 Python `idp-platform`），并书面确认 TMS 与 Parcel 都将使用。`v0.2` 原语实现被 `v0.1.0` 稳定发布门禁阻塞，而平台库现在就要动工；一个内聚的编号能力若劈在框架与平台库两侧，每次令牌或算法演进都要跨过发布节奏最慢的框架双消费者门禁。

## 决定

- 编号原语（模板 DSL、Feistel 加扰、校验位、原子序列分配及其技术表迁移资产）不再进入框架，随编号能力整体归 `idp-platform-go`。
- 撤回 `v0.2` 编号原语提案：[对应决策简报](../design/v0.2-numbering-primitives-decision-brief.md)标记为已取代；框架公共包保持 `v0.1` 的八个公共包范围，无新增计划。
- ADR-0010 的边界决定继续有效并收紧：平台能力与编号原语都不进入框架；框架不导入平台库。
- 已确认的消费者用例（TMS 运输任务编号、Parcel 对账单号）与 Python 令牌词汇表兼容约束由 `idp-platform-go` 承接。
- `idp-platform-go` 从框架视角是一个普通消费者：只导入公共 API，不获得特殊接口，不豁免兼容性契约。

## 后果

- 框架 `v0.1` 范围与 RC 线不受扰动，API 快照与 18 个门禁不重开。
- 编号能力单一归属、单一发布节奏，平台库演进不受框架双消费者门禁约束。
- 框架失去"纯标准库编号原语"这一潜在公共包；未来若有绕开平台库的场景需要，必须重新立项并推翻本 ADR。

## 考虑过的替代方案

- 维持 `v0.2` 简报、平台库等框架发布后再动工：阻塞平台库，违背维护者时限要求。
- 平台库先内嵌一份原语、框架 `v0.2` 落地后切换：双份实现加一笔迁移账，且框架包从此失去存在理由。
