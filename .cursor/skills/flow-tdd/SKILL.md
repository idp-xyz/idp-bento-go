# 测试驱动

红 → 绿是循环本身。本文是让这个循环产出值得留下的测试的参考：什么算好测试、测试放在哪、反模式、循环的规则。每一节在每一圈都适用，在循环之前和之中查。

## 先读画像

`.cursor/test-profile.md` 声明本仓库的语言、断言风格、测试工具和依赖方向。`.cursor/repo-profile.md` 的「缝」一节声明公共缝在哪，术语表路径让测试名和接口用词对齐仓库用语。开始之前先读它们。

画像不存在时，先走 `flow-grilling` 把这些问清楚并写下来。

## 什么算好测试

测试通过公共接口验证**行为**，不碰实现细节。实现可以整个换掉，测试留着不动。好测试读起来像一份规格——`TestOutboxClaimSkipsLockedRows` 直接告诉你存在什么能力——它能扛过重构，因为它只关心接口这一侧看得见的东西。

## 缝——测试放在哪

**缝**是你观察行为的公共边界：在那里能看到行为，而不需要伸手进去。测试活在缝上。本仓库的缝由 `.cursor/repo-profile.md` 声明。

**只在事先约定的缝上写测试。** 动手之前先写下这轮要测哪些缝，和用户确认。测不完所有东西，事先约定缝是让测试投入落在关键路径和复杂逻辑上、而不是摊平到每个边角的办法。

问："公共接口是什么，我们测哪几条缝？"

## 反模式

**耦合实现**——给内部协作者打桩、测私有函数、或者从侧信道验证（直接查数据库而不是走接口）。判据是：重构时测试挂了，但行为根本没变。

**同义反复**——断言用和代码同样的方式重算期望值，于是它按构造必然通过，永远不可能和代码唱反调。期望值要来自独立的事实来源：一个已知正确的字面量、一个手工推演过的例子、决策文档里写死的语义。

**横切**——先把测试全写完，再去写实现。批量写出来的测试验证的是**想象中**的行为：你测的是形状而不是真实行为，测试对真实变化变得迟钝，而且你在理解实现之前就把测试结构定死了。改成**纵切**：一个测试 → 一份实现 → 再来一轮，每个测试都是一发曳光弹，根据上一轮学到的东西调整下一轮。

**假实现顶替真实依赖**——为了省事给合同测试塞一个内存替身。假实现绕开真实的存储、锁、约束和失败路径，产出的测试只能证明假实现能用。画像里若已就此做过决定，遵守它。

## 循环的规则

**先红后绿。** 先写失败的测试，然后只写刚好让它通过的代码。每一圈只服务眼前这个测试。

**一次一片。** 一条缝、一个测试、一份最小实现，一圈只做这些。

**重构属于评审阶段。** 红 → 绿的实现循环里只有这两步。

**共识先行。** 如果这一片背后的设计决定还没确认，先走 `flow-grilling`。

## 边界

测试夹具只表达技术语义，遵守画像「硬边界」一节列出的所有权边界。需要一个领域对象来驱动测试时，造一个最小类型，别把别处的业务语言搬进来。
