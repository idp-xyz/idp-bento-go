# 测试驱动

红 → 绿是循环本身。本文是让这个循环产出值得留下的测试的参考：什么算好测试、测试放在哪、反模式、循环的规则。每一节在每一圈都适用，在循环之前和之中查。

探索代码时读 `docs/design/domain-language.md`（如果存在），让测试名和接口用词对齐仓库术语；改到哪个区域就遵守那个区域的 ADR。

## 什么算好测试

测试通过公共接口验证**行为**，不碰实现细节。实现可以整个换掉，测试留着不动。好测试读起来像一份规格——`TestOutboxClaimSkipsLockedRows` 直接告诉你存在什么能力——它能扛过重构，因为它只关心接口这一侧看得见的东西。

`AGENTS.md` 把这条抬成了硬要求：公共 API 必须有真实消费者用例和兼容性测试证明。一个没有消费者用例支撑的公共 API，缺的不是测试，是存在的理由。

## 缝——测试放在哪

**缝**是你观察行为的公共边界：在那里能看到行为，而不需要伸手进去。测试活在缝上。

本仓库的缝是包边界：`domain`、`repository`、`eventing`、`application`、`testkit` 的导出面。适配器（`postgres` 及其子包）的缝是它实现的那个端口，它的 SQL 留在缝的另一侧。

**只在事先约定的缝上写测试。** 动手之前先写下这轮要测哪些缝，和用户确认。测不完所有东西，事先约定缝是让测试投入落在关键路径和复杂逻辑上、而不是摊平到每个边角的办法。

问："公共接口是什么，我们测哪几条缝？"

## 怎么写

标准库 `testing`，got/want 断言，表驱动配 `t.Run`；端口语义走 `testkit` 的合同运行器，用 `testkit` 的确定性替身消除时间和 ID 的不确定性。具体写法和范例见 [GO-TESTS.md](GO-TESTS.md)。

## 反模式

**耦合实现**——给内部协作者打桩、测私有函数、或者从侧信道验证（直接查数据库而不是走接口）。判据是：重构时测试挂了，但行为根本没变。

**同义反复**——断言用和代码同样的方式重算期望值，于是它按构造必然通过，永远不可能和代码唱反调。期望值要来自独立的事实来源：一个已知正确的字面量、一个手工推演过的例子、决策简报里写死的语义。

**横切**——先把测试全写完，再去写实现。批量写出来的测试验证的是**想象中**的行为：你测的是形状而不是真实行为，测试对真实变化变得迟钝，而且你在理解实现之前就把测试结构定死了。改成**纵切**：一个测试 → 一份实现 → 再来一轮，每个测试都是一发曳光弹，根据上一轮学到的东西调整下一轮。

**假实现顶替真实端口**——给合同运行器塞一个内存 Store 图省事。`docs/design/testkit-contract.md` 已经拒绝过这条路：内存实现绕开真实 SQL、锁、约束和提交失败，产出的测试只能证明假实现能用。

## 循环的规则

**先红后绿。** 先写失败的测试，然后只写刚好让它通过的代码。每一圈只服务眼前这个测试。

**一次一片。** 一条缝、一个测试、一份最小实现，一圈只做这些。

**重构属于评审阶段。** 红 → 绿的实现循环里只有这两步。

**共识先行。** 如果这一片背后的框架决定还没确认，先走 `flow-grilling`。

## 边界

测试夹具只表达技术语义。**TMS 与 Parcel 的业务语言、规则和数据不得进入本仓库**——需要一个聚合或事件来驱动合同运行器时，造一个最小类型，像 `domain/event_test.go` 里的 `testEvent` 那样。

`backup/` 是本地历史快照，找既有测试范例时从活着的包里取。
