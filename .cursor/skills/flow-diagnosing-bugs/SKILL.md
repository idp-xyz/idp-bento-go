# 排障

对付难缠的 bug 的纪律。跳过某个阶段时说明理由。

`.cursor/repo-profile.md` 的术语表路径能给你相关模块的心智模型，改到哪个区域就看那个区域的 ADR。「验证」一节给出本仓库的最小相关命令和完整门禁。

## 阶段一 —— 建立反馈回路

**这一阶段就是这个技能本身**，其余都是机械动作。只要有一个**紧**的通过/失败信号——一个会因为**这个** bug 变红的信号——你就能找到原因；二分、验证假设、埋点都只是在消费它。没有它，盯着代码看多久都没用。

在这里投入不成比例的精力。**放开手脚，有创意，不要放弃。**

### 构造回路的办法，大致按这个顺序试

1. **失败的测试**，放在能触到 bug 的那条缝上。
2. **命令行调用**配一份固定输入，把 stdout 和已知正确的快照做 diff。
3. **一次请求**打到跑起来的本地服务。
4. **重放抓到的现场**。把真实的请求、载荷或事件日志存到磁盘，隔离地重放进那条代码路径。
5. **一次性夹具**。起一个最小子集（一个服务，依赖打桩），用一次函数调用就能走到出问题的路径。
6. **属性或模糊测试回路**。如果症状是"有时候结果不对"，跑一千个随机输入，找那个失败模式。
7. **二分夹具**。如果 bug 出现在两个已知状态之间（提交、数据集、版本），把"切到状态 X、检查、重复"自动化，让 `git bisect run` 能跑。
8. **对照回路**。同一个输入分别过旧版和新版（或两套配置），diff 输出。
9. **人在环里的脚本**。最后手段。如果非要人来点，也用脚本驱动**他**，让回路保持结构化，人的输出回流给你。

回路建对了，bug 就解决了九成。

### 把回路调紧

把回路当产品做。有了**一个**回路之后，**调紧**它：

- 能更快吗？（缓存初始化、跳过无关准备、缩小测试范围。）
- 信号能更锐利吗？（断言那个具体症状，而不是"没崩"。）
- 能更确定吗？（钉住时间、固定随机种子、隔离文件系统、冻结网络。）

一个三十秒的抖动回路比没有强不了多少；一个两秒的确定回路是调试超能力。

### 非确定性的 bug

目标不是干净复现，而是**更高的复现率**。触发一百次、并行跑、加压力、收窄时间窗、插入 sleep。50% 概率的 bug 可以调，1% 的不行——把复现率一直抬到可调为止。

### 实在建不出回路时

明确说出来并停下。列出你试过什么。向用户要三样之一：能复现的环境访问权、抓到的现场（日志、内存转储、带时间戳的录屏），或者临时加生产埋点的许可。有回路再进阶段二。

### 完成判据 —— 一个能变红的紧回路

阶段一完成的标志是：你能说出**一条命令**——脚本路径、测试调用、一次请求——而且**已经至少跑过一次**（把调用和输出贴出来），它同时满足：

- **能变红**——它走的是真实出问题的代码路径，断言的是**用户描述的那个症状**，所以它会因这个 bug 变红、修好之后变绿。"跑起来不报错"不算，它必须能抓住这个具体的 bug。
- **确定**——每次跑结论一致（抖动的 bug 则是钉住的高复现率）。
- **快**——秒级。
- **能无人值守跑**——需要人参与时用脚本驱动。

如果你发现自己在这条命令存在之前就开始读代码构思理论，**停下——直接跳到假设正是这个技能要防的失败**。

## 阶段二 —— 复现并最小化

跑回路，看着它变红。

确认三件事：回路产生的是**用户**描述的那个失败，而不是旁边那个碰巧也会挂的；失败可以多次复现（抖动的 bug 则复现率足够调试）；症状已经原样记录下来（错误信息、错误输出、耗时），供后面的阶段核对修复是否真的对上了。

然后把复现场景缩到**仍然会变红的最小规模**。输入、调用方、配置、数据、步骤，一次砍一样，每砍一刀重跑回路，只留下承重的部分。

这么做有两个收益：最小复现缩小了阶段三的假设空间，而且它本身就是阶段五那个干净的回归测试。

做完的标志是**剩下的每一样都是承重的**——再拿掉任何一个，回路就变绿。复现和最小化都做完再往下走。

## 阶段三 —— 提假设

在验证任何一个之前，先生成**三到五个排好序的假设**。只想一个会让你锚死在第一个看起来合理的想法上。

每个假设都要**可证伪**，写出它的预测：

> 格式："如果原因是 X，那么改动 Y 会让 bug 消失／改动 Z 会让它更严重。"

说不出预测的，那是感觉，删掉或磨锐它。

**把排好序的列表先给用户看。** 他们的领域知识经常能瞬间重排（"我们刚给第三条那块发过版"），或者知道哪些已经排除过了。检查点很便宜，省时间很多。用户不在就按你的排序往下走。

## 阶段四 —— 埋点

每个探针对应阶段三的一个具体预测。**一次只改一个变量。**

工具优先级：能用调试器或交互式检查就用，一个断点胜过十行日志；其次是在能区分假设的边界上打靶向日志。别"全都记下来然后 grep"。

**每条调试日志打唯一前缀**，比如 `[DEBUG-a4f2]`。收尾时一次 grep 就能清干净——打了标记的日志会死，没打的会活下来。

**性能分支**：性能回归靠日志通常是错的。先建立基线测量（计时夹具、profiler、执行计划），然后二分。先测量，后修。

## 阶段五 —— 修复并加回归测试

回归测试写在修复**之前**——前提是存在**正确的缝**。

正确的缝是指测试能在真实调用点上重现 bug 的模式。如果唯一可用的缝太浅（bug 需要多个调用方，而那里只能测单个；单元测试重现不出触发它的那条链），在那里加回归测试只会给出虚假的信心。

**没有正确的缝，这件事本身就是一个发现。** 记下来——代码结构正在阻止这个 bug 被锁死。

缝存在时：把最小复现变成那条缝上的失败测试 → 看它失败 → 应用修复 → 看它通过 → 拿阶段一的回路对着**原始的、未最小化的**场景再跑一遍。

## 阶段六 —— 收尾与复盘

宣布完成之前逐项确认：原始复现不再复现（重跑阶段一的回路）；回归测试通过，或者缝的缺失已记录在案；所有 `[DEBUG-...]` 埋点已清除（grep 那个前缀）；一次性夹具已删除；那个被证实的假设写进了提交信息，让下一个调试的人能学到。

**然后问：什么本来能防住这个 bug？** 如果答案涉及结构变更（没有好的测试缝、调用方纠缠、隐藏耦合），把具体情况写成建议。这个建议在修复落地**之后**才提——那时你掌握的信息比开始时多得多。
