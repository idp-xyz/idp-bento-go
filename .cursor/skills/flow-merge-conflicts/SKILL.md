# 解决合并冲突

按**意图**解决冲突，同时保住工作树里那些和这次操作无关的改动。

`.cursor/repo-profile.md` 的「验证」一节给出本仓库的检查命令。

## 1. 认清操作和基线

确认 git 正在做的是 merge、rebase 还是 cherry-pick。看 `git status`、历史、未合并路径，以及所有已暂存和已修改的内容。

把**这次 git 操作带来的改动**和**操作之前就存在的无关工作**区分开。后者全程保持原样：不暂存、不重写、不提交。这个区分做不出来时，停下来问。

## 2. 找到一手依据

对每处冲突，弄清两边各自为什么改、这次操作想达成什么。先读相关的提交，再按画像「规格来源」一节列出的顺序找进一步的依据。

## 3. 判断继续是否成立

出现下列证据时停下：合并的是错的分支或提交、基线已经陈旧、这次操作本身是误触发、或者要解出来就得凭空发明行为。把证据讲清楚，建议中止或重来。

**回滚命令需要用户明确授权才能执行**——`git merge --abort`、`git rebase --abort` 及同类命令都是。

## 4. 逐块按意图解决

两边意图兼容时都保留。不兼容但目标结果已经明确时，选符合那个结果的一边，并把代价说出来。行为以两边已有的为准。

解完一个文件，确认里面没有冲突标记，然后**用显式路径**只暂存这一个文件：

```
git add <具体路径>
```

暂存范围就是这些显式路径，`git add .` 和 `git add -A` 会把无关工作一起卷进来。

## 5. 跑检查

按画像「验证」一节跑：先最小相关的，通过后跑完整门禁。格式化优先用只检查模式或限定路径的模式，已解决路径之外的格式化产物不进索引。

只修由这次解决引入的失败，工作树里的无关改动保持不动。

## 6. 进入下一步之前核对索引

确认没有未合并路径残留。

索引里应该只有两样东西：git 作为操作的一部分自己暂存的改动，以及第 4 步显式暂存的冲突路径。操作之前就存在的无关工作，以及顺带产生的格式化输出，都不该在里面。

如果有无关改动会进到这次的 merge commit 或 rebase 后的提交里，停下来问用户怎么分离。

## 7. 一次只推进一个 git 步骤

merge：索引范围核对干净、检查通过之后，才创建 merge commit。

rebase 或 cherry-pick：跑正常的 continue 命令，之后每出现一次新冲突就把这套流程重走一遍，直到操作结束。

最后汇报：有意保留的取舍是什么，以及哪些检查没能跑起来。
