# 代码评审

对某个固定点到当前工作树之间的**有效改动**做双轴评审：

- **标准轴**——代码符合本仓库记录在案的规范吗？
- **规格轴**——代码忠实实现了那个决定吗？

两轴分开跑、分开报。一个改动可能标准全对但实现了错的东西，也可能实现完全正确却违反了仓库约定。合并两轴会让其中一个盖住另一个。

## 先读画像

`.cursor/repo-profile.md` 的「评审标准」一节声明标准轴的依据文档，「规格来源」一节声明规格轴按什么顺序找依据。开始之前先读它。

## 1. 钉住基线

用户说的那个点就是固定点——commit SHA、分支名、tag、`main`、`HEAD~5` 都行。用户没说就问。

解析一次，全程复用：

1. `git rev-parse <固定点>` 确认它能解析。
2. `git merge-base <固定点> HEAD`，把结果记作**评审基线**。
3. 有效树：`git diff --no-ext-diff --binary <评审基线>`。它比较基线树和工作树，所以已提交、已暂存、未暂存的内容净和都在里面。
4. 分层留证：`git diff --cached --no-ext-diff --binary <评审基线>` 是基线到索引，`git diff --no-ext-diff --binary` 是索引到工作树。有了这两层，一个只存在于索引里的改动就不会因为工作树的反向编辑而消失。有效树是最终内容，分层只是来源，同一个 hunk 只算一次。
5. `git ls-files --others --exclude-standard` 列出未跟踪文件，每一个都当作新增文件通读全文。
6. `git log <评审基线>..HEAD --oneline` 和 `git status --short` 记下上下文。

至少要有一层非空，或者未跟踪列表非空。坏的 ref 和真的空改动在这一步就该失败。

修复和复审全程复用同一个评审基线，编辑或提交之后也不往前挪。

## 2. 找规格

按画像「规格来源」的顺序找。找不到就问用户；用户说没有，就跳过规格轴，在报告里写明。

## 3. 两轮隔离评审

本工作区禁止并发 subagent，两轮串行跑。隔离靠纪律维持：**跑标准轮时只带标准轮的材料，跑规格轮时只带规格轮的材料**，前一轮的结论在聚合之前不进入后一轮的判断。

**标准轮**——材料是画像列出的标准文档，加上下面的气味基线。报告按文件或 hunk 组织，每条说明：违反了哪条成文标准（引用文档和规则原文），或者命中了哪个气味（点名并引用 hunk）。区分硬违规和判断题——成文标准的违反可以是硬的，气味永远是判断题。成文标准和气味冲突时，成文标准赢。工具已经把守的跳过。

**规格轮**——材料是找到的规格。报告三类：规格要求了但缺失或只做了一半的；改动里做了但规格没要求的（范围蔓延）；看起来实现了但实现得不对的。每条引用规格原文。

### 气味基线

即使仓库什么都没写，标准轮也带着这套判断。每条读作*它是什么* → *怎么修*：

- **可疑命名**——函数、变量或类型的名字没有透露它做什么或装什么。→ 改名；起不出诚实的名字说明设计还浑浊。
- **重复代码**——同一个逻辑形状出现在改动的多个 hunk 或文件里。→ 抽出共享形状，两边都调它。
- **依恋情结**——一个方法访问别的对象的数据比访问自己的还多。→ 把方法搬到它依恋的数据那边。
- **数据泥团**——同几个字段或参数总是一起出现，那是一个想出生的类型。→ 打包成一个类型传递。
- **基本类型偏执**——用基本类型或字符串顶替一个配得上自己类型的领域概念。→ 给这个概念一个小类型。
- **重复的分支**——同一个类型上的 `switch` 或 `if` 级联在改动里反复出现。→ 换成多态，或者一张两边共用的映射表。
- **霰弹式修改**——一个逻辑改动逼你在很多文件里零散地改。→ 把一起变的东西收进一个模块。
- **发散式变化**——一个文件或模块因为几个不相干的理由被改。→ 拆开，让每个模块只因一个理由变化。
- **投机通用性**——为规格没提的需求加的抽象、参数或钩子。→ 删掉，内联回去，等真实需求出现再说。
- **消息链**——`a.b().c().d()` 这种调用方本不该依赖的长导航。→ 把这趟走法藏进第一个对象的一个方法里。
- **中间人**——一个大部分工作只是转发的类型或函数。→ 去掉它，直接调真正的目标。
- **拒绝的遗赠**——子类型或实现忽略、覆盖了它继承来的大部分东西。→ 改用组合。

## 4. 聚合，保持两轴分开

用 `## 标准` 和 `## 规格` 两个标题分别呈现，保持原样或轻度整理。**不要合并、不要跨轴重排**——两轴分开正是为了防止这件事。

结尾一行小结：每轴各多少条发现，以及**各自轴内**最严重的那条。不要跨轴评选最严重的。

## 5. 需要修的时候才闭环

只要求评审就是诊断：报完发现就停。用户明确要求处理发现，或者调用方把评审当作修复门禁时，才进入修复循环。

对每条发现：

1. 拿它去对照引用的标准或规格，以及真实代码，验证它成立。
2. 修掉每一条确认成立且可行动的发现。判断题如果会改变产品意图或架构，先问再改。误报要留一句简短理由，别默默丢掉。
3. 每批修复之后跑最小相关的测试或类型检查，声明这批完成之前跑一遍仓库的完整验证。
4. 用**同一个评审基线**和当前工作树，把受影响的那一轴重新跑一遍。修复同时可能影响正确性和范围时，两轴都重跑。
5. 重复到没有可行动的发现，或者卡在等用户决定。

最终回复仍然保持 `## 标准` 和 `## 规格` 分开。每一节先列未解决的，再列循环中已解决的及其验证方式。结尾给出每轴小结和实际执行的验证命令与结果。还有可行动的发现时，别声称评审通过。
